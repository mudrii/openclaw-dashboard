# OpenClaw 2026.8.2: dashboard gap analysis and implementation plan

Assessment date: 2026-09-05. Repository: `openclaw-dashboard`, HEAD `f0c954a`, source VERSION `v2026.7.12`. Runtime state: `$HOME/.openclaw`.

## Recommendation

Ship a compatibility release before expanding the UI. The dashboard currently loses migrated sessions, cannot account reliably for current usage, misses cron jobs because its service uses a different CLI/authentication context, and exposes contradictory gateway status. New memory, task, automation and policy views will be useful only after these sources are dependable.

Retain the existing zero-dependency Go server and embedded SPA. Use OpenClaw-owned JSON projections through a bounded CLI/Gateway bridge; avoid coupling the dashboard to private SQLite tables. Expand the existing runtime and configuration views before building separate panels. Use links to native OpenClaw for advanced session workspaces, approval/configuration workflows and widgets until there is a concrete need to duplicate them.

This assessment produced documentation only. No application implementation, OpenClaw configuration, service definition, deployment, approval decision, upgrade or database repair was changed. Calling the dashboard's normal GET refresh endpoints refreshed its generated cache; OpenClaw diagnostic reads can also refresh internal diagnostic/usage caches.

Supporting evidence:

- [Release and API research](openclaw-2026.8.2-release-research.md): official release distinctions and tag-pinned integration contracts.
- [Dashboard source audit](openclaw-2026.8.2-dashboard-code-audit.md): source locations, compatibility defects and existing test seams.
- Runtime observations below are from bounded commands and HTTP reads performed during this assessment. Counts are snapshots, not permanent invariants. Private transcript text, credential values and messaging identifiers are intentionally omitted.

### Concrete failures requiring follow-up

1. **Dashboard collector identity/authentication mismatch.** Fresh `/api/system` reports host CLI 9.1, healthy HTTP probes, and a gateway device metadata change awaiting approval. Host `cron list --all --json` fails with `missing scope: operator.read`. The same container-targeted cron command succeeds. Fix collector targeting and the intended device identity; do not broadly approve unknown devices or give the whole dashboard admin scope.
2. **Local 8.2 SQLite inspection failure.** Container `tasks list`, `tasks flow list` and `database ownership status` failed with read-only snapshot stabilization/database-lock errors. `gateway call tasks.list` succeeds. The cause of locking was not established; there is no evidence here that the live database is corrupt. Prefer the working gateway-owned task read path, and investigate the local CLI/storage interaction separately before relying on those local inspection commands.
3. **Dashboard compatibility failures.** After its background refresh completed, `/api/refresh` still returned `sessionCount=0`, `sessions=null`, `crons=null`, memory policy null, and a synthetic agent ID `default`; current runtime queries have real sessions, four cron definitions, active memory configuration and agent `main`.
4. **Chat route unavailable.** A read-only GET to the exact upstream `/v1/chat/completions` path returned 404 and the config has no explicit HTTP endpoint enablement. No model turn was submitted, so an end-to-end chat POST was not tested. The current chat transport should be treated as unavailable until capability/auth checks prove otherwise.

The first dashboard GET returned an old cache from September 2 and triggered its normal background refresh. Later data was current to September 5. This is expected on-demand refresh behavior, not evidence that the scheduler is permanently stuck. The compatibility discrepancies persisted after refresh.

## 4. Dashboard improvements ranked by impact

### P0: restore correctness

**Authoritative sessions.** Replace `loadSessionStores` as the primary enumerator. Prefer Gateway `sessions.list` for UI semantics and access-aware fields; use CLI session inventory as an explicit compatibility/diagnostic source. Local CLI returns three stored entries, including a cron run alias; Gateway UI listing returns two rows. These are different projections, not an off-by-one bug. The dashboard currently excludes cron `:run:` aliases and sessions older than 24 hours. New tests must compare like-for-like filters and show scope/filter labels.

Use `hasActiveRun` for running state, retain `activeRunIds` semantics, preserve `agentId`, provider/model override, visibility, placement, and known/unknown context usage. Never turn unknown total tokens into a zero-percent context bar.

Source: `internal/apprefresh/refresh_sessions.go:21`, `session_model_cache.go:143`, `web/index.html:1766`.

**Authoritative usage and explicit cost completeness.** Replace JSONL-only aggregation with `sessions.usage`/`usage.cost` through Gateway RPC. A scoped August 7–September 5 query returned 81,218 tokens and 10 entries without prices after its cache became fresh. Subsequent all-agent queries were still refreshing and produced partial totals. This is direct evidence for preserving scope and `cacheStatus`; it is not a final billing reconciliation. The dashboard instead reports $0 today and $0.02 all-time from its current legacy-derived path.

Represent token totals, known cost, missing cost count and collection/cache completeness separately. Missing custom-model prices require operator-supplied verified rates if estimates are desired; never manufacture prices. Disable or qualify spend projections/alerts when inputs are incomplete. Distinguish reported cost from estimated cost. Avoid double counting migrated history and legacy cache records.

Source: `internal/apprefresh/token_usage_cache.go:36`, `refresh.go:362`, `refresh_tokens.go:13`.

**Runtime identity, access and gateway truth.** Display host CLI version, selected collector CLI version, actual gateway version and stable available version separately. Represent liveness, readiness, authenticated access and service/supervisor state independently. The existing `ParseGatewayStatusJSON` maps a missing local service to offline and ignores successful RPC/nested version fields. Do not use a container PID with host `ps`.

Source: `internal/appsystem/system_service.go:417`, `:799`, `internal/appservice/launchd.go`, `internal/appservice/systemd.go`.

**Honest collection errors and version metadata.** Per-collector status must distinguish success-empty, partial, stale, unavailable, unsupported and permission denied. Preserve last-good data with timestamps. Cron/subagent source failures currently collapse to empty/null. npm `/openclaw/latest` returned 105,475 bytes while the decoder allows 65,536, matching repeated `unexpected EOF` logs. The verified `/-/package/openclaw/dist-tags` response is only 69 bytes and contains `latest`; use that small contract or a separately bounded metadata limit.

Source: `subagent_tasks.go:87`, `refresh_crons.go:216`, `internal/appsystem/system_service.go:80`, `:1032`.

### P1: make existing views complete

**Memory and effective configuration.** Support `memory.search` and legacy `agents.defaults.memorySearch`; use effective runtime agent identity/workspace; display model policy separately from catalog entries. Show configured provider/model, index dirty state, eligible/indexed files, chunks, vector/FTS health and dreaming audit summary. Here the memory provider is Ollama, model `qwen3-embedding:0.6b`; index dirty is actionable information the current dashboard hides. Deep embedding execution is a separate explicit diagnostic, not every-poll behavior.

**Automation operations view.** Existing cron CLI support should be retained. Inventory must include disabled jobs (`--all`) and pagination when required. Current deployment has three enabled definitions and one disabled heartbeat. Add run history, task/session links, payload kind (including exec/system/agent forms), timezone, retry/skip diagnostics and delivery outcome. A job configured with no delivery must not get a failure badge for `not-requested`. Use `cron runs --id ...` for the pinned 8.2 CLI, not newer positional syntax.

**Task explorer.** Extend the subagent table into a filterable task view for subagent/cron/ACP/CLI, keeping the subagent filter. Retain stable task/run/session identities, terminal outcome, progress, delivery state and owner. Gateway RPC rows can use `status=completed`, while CLI/status aggregates use `succeeded`; preserve raw values and normalize deliberately. RPC inventory also included migrated run-history records beyond the status summary's 21 tasks, so counts must be reconciled by semantic identity and scope rather than assumed equal. The existing row key uses truncated title and minute timestamp and can collide.

**Plugins, skills and channels.** Overlay effective runtime inventory on config. Show loaded/disabled/blocked/failed plugin state and relevant diagnostics; skills eligible/model-visible/disabled state; per-account channel health. A healthy account should not hide another account's failure. Retain current liveness/readiness and catalog collectors.

**Logs and diagnostics.** Add bounded gateway `logs.tail` via the runtime bridge when supported, retain local files/journald for other deployments, and label source/freshness. Expand the existing runtime card with task audit, model/auth diagnostics, sanitized security findings and backup status if returned. Absence is unknown/unsupported, not a fabricated healthy result.

### P2: optional control and richer work context

Add read-only goals/progress and placement first. `sessions.list` can carry `goal`; `progressCard.get` and `board.get` expose session-owned progress/boards. Workboard is an optional plugin with its own methods. Hide unsupported controls or explain that the plugin is unavailable.

Initially link to native OpenClaw for approvals, config changes, session workspaces, widgets and device setup. If actions are implemented later, choose a narrow set: automation enable/disable/run, exact-run cancellation and approval inspection. Require server-side authorization, request-origin/CSRF protection, scope checks, operation identity and audit records. Existing localhost binding and CORS are not an authorization system for write APIs.

Restore basic AI chat capability/auth handling separately from full chat parity. Native persistent conversations, streaming, tools, attachments and placement-aware chat are a substantial product expansion. Do not enable a disabled upstream endpoint or resolve and expose secrets merely to make a health indicator green.

## 5. Proposed technical design

```text
Embedded SPA
    | /api/refresh + /api/system + bounded detail endpoints
Dashboard normalized snapshots (data + source/scope/freshness/error)
    | shared command execution + capability checks
Selected OpenClaw CLI -> gateway call -> selected running Gateway
    |                                  |
    | optional legacy read fallback    + canonical runtime-owned SQLite state
    + explicit legacy installations
```

The first implementation should invoke the installed CLI's existing Gateway client, which already handles the v4 wire protocol and authentication. A long-lived direct WebSocket client would add protocol/dependency maintenance to a zero-dependency Go repository. Reconsider only after measuring subprocess latency; browser updates can remain cached polling, or use same-origin server-sent events later if worthwhile.

### Boundaries and ownership

- Add a small `internal/appopenclaw` boundary only for shared target selection, bounded command execution, RPC invocation and capability/error classification. It has multiple existing consumers, so this is a concrete shared seam. Keep mapping/aggregation in `apprefresh`, system health in `appsystem`, chat in `appchat`, service environment in `appservice`, config in `appconfig` and HTTP handling in `appserver`.
- Use a concrete target configuration: CLI path, native/container mode, selected container/profile and non-secret endpoint metadata. Reuse current CLI resolution and inherited environment semantics where possible. Pass argv directly; never accept arbitrary browser-supplied commands or RPC method names.
- Preserve a fixed allowlist of backend operations. Start with `operator.read`; classify admin-only diagnostic methods as unavailable under that scope. A capability probe must not invoke model/tool execution.
- Use one source per domain/scope and report it. Successful empty modern data must not fall back to old files. Modern source failure may retain a marked last-good snapshot; legacy fallback needs explicit supported-version/source evidence.
- Read only documented public projections; no direct SQLite schema joins, migrations, ownership claims or in-process database driver.
- Keep additive response changes compatible with existing `data.json` consumers where possible. Add a response schema version and section metadata. If money/null semantics change, update backend, embedded UI and documented wire contract together.
- Bound command duration, stdout/stderr, row count and concurrency; share in-flight requests and cache results. Use fast health/session/task cadence and slower diagnostics/catalog/memory cadence. Tune budgets using measured native versus Podman latency.
- Preserve unknown enum values, null usage and absent optional fields. `activeRunIds: []` and omitted `activeRunIds` have different meanings. Method-discovery lists are conservative; known documented RPCs such as `sessions.usage` may be callable even when not advertised.
- Project public fields explicitly and redact errors before saving or returning them. Never return resolved tokens, auth profiles, raw config, or arbitrary diagnostic objects by default. Shared-user support would require access-controlled caches, not one global all-agent snapshot.

Estimates below are planning ranges for one engineer including focused tests/review, not delivery commitments. Auth/environment issues or undocumented response drift can expand them. Each milestone should be a reviewable PR; application of runtime/service changes is a separately visible step within implementation.

| M1: sessions and accounting | Session snapshot adapter, active/placement fields, usage RPC, cost completeness, legacy compatibility | No legacy files required; known activity appears; scope/pagination correct; missing prices and warming caches never shown as complete zero spend | 3–5 days |

## 7. Verification and rollout

Required contract cases:

- Legacy JSON-only, SQLite-era no-legacy-files, mixed migrated history and custom agent paths.
- Native CLI, host 9.1/container 8.2, missing CLI, unavailable container, missing scope, pending device approval and gateway outage.
- Valid empty list, null/absent fields, new enum values, pagination, capped output and timeout.
- Session UI rows versus physical aliases; no active run versus unknown run identity; correct provider override and placement.
- Usage cache warming/fresh, different agent scopes, unavailable prices, real zero prices, input/output/cache categories and UTC/local-day boundaries.
- Duplicate task titles/timestamps, stable IDs, CLI versus RPC status vocabulary, imported task history and incomplete delivery.
- Current memory.search versus older schema; effective model allowlist; one failed channel account alongside a healthy account.
- HTTP ready + service not installed; HTTP healthy + RPC denied; host and container PIDs kept distinct.
- Secrets absent from JSON, generated cache, logs and UI; HTML-safe labels; no arbitrary executable/RPC surface.

Use existing fake command/HTTP seams and small recorded fixtures. Preserve root facade and zero third-party dependencies. Backend changes should run `make vet` and `make test`; release gate is the repository's `make check`. UI changes require rebuild because `web/index.html` is embedded, plus a browser check for filtering, errors, stale state and unknown money values. Avoid repeated paid model/embedding probes in automated tests.

For live acceptance, compare the same agent scope, time range, cache state, disabled-job setting and session filters against the selected gateway. Do not require unlike inventory projections to have identical counts. Verify the dashboard service's actual environment rather than only the interactive shell.

Roll out dashboard-only changes first with the prior binary/config recoverable. No OpenClaw database migration is needed for these dashboard read adapters. If collector permissions or container targeting need adjustment, document the exact intended identity and verify read access after the change. Keep 8.2 fixtures even when adding a separate 9.1 compatibility job.

## 8. Deliberately deferred items and limits

- Automatic OpenClaw upgrades/restarts, database repair, deletion of recovery artifacts, backup restore, broad config editors and mass approval actions.
- A new frontend framework, third-party SQLite driver or direct WebSocket protocol implementation without measured need.
- Full native Home/chat/workspace parity, arbitrary MCP app embedding, cloud provisioning and team administration.
- 9.1-only features such as newer CLI config compare-and-swap flags, `memory reset`, and `cron.skipMissedJobs`. These need a separately verified version gate. [9.1 release](https://github.com/openclaw/openclaw/releases/tag/v2026.9.1)

Not verified in this assessment: provider inference, end-to-end AI chat, embedding execution, backup restore, node/browser actions, Workboard activation, destructive migration integrity, or the root cause of the observed local SQLite inspection lock. These limits do not block the verified read-only integration plan.

Final decision: correct the runtime boundary and session/usage accounting first; then expose memory, task, automation and policy information already relevant to this installation. Preserve the dashboard's focused operational role while making advanced native OpenClaw features easy to reach.
